# ADR-0005: content enters tengai by kernel replay of an export

Status: proposed 2026-11-20 (the first transplant, with measurements, decides whether it is adopted).

## Context
Tengai builds on Lean core alone (I3), loads under an absolute cap (C_load) and must hold a strong amount of Tengoku. Measured on 330 Tengoku theorems (tenro `tools/promote/sizing.py`): none is
closed over Lean core; a theorem needs a median of about 12,500 constants outside it, 10 theorems need 35,000 distinct constants together, 100 need 78,500 and 330 need 87,600 (5.0M if nothing were shared).
Content is therefore one shared foundation of about 80,000 constants plus about 40 new constants a theorem. A proof written against Mathlib cannot be re-proved on Lean core by source copying.

## Decision
A promotion is a **kernel replay** of a `lean4export` file (format 3.x), done by `tengai-replay`: every declaration goes through `addDecl`, so a wrong term is refused whatever produced it (I1); what Lean core already
holds must have the same type and is not added again; the result is a built `.olean` (`TengaiData.<Topic>`), which a prover imports with the snapshot on `LEAN_PATH`. The release is the `.olean` snapshot
(`docs/design.md`). The replay tool imports `Lean`; no library module imports it and the modules it writes do not, so the import stays as small as the content. What the kernel does not hold but elaboration needs is carried in a second, small file
(`tengai-extinfo` reads it where the constants were built, `tengai-replay --ext` puts it back): reducibility, projection information, classes, instances (global, or scoped with `--scoped-instances`), structure
information (the fields and parents: `{ x := 1 }`, `{ p with x := 2 }`, `p.x` through a parent) and the binder names and annotations that the export's term sharing replaced. Nothing else is registered: no simp set,
no `ext`, `norm_cast` or `elab_as_elim` entry, no notation (macros and elaborators are code, which a replay does not carry). The equation lemmas of recursive definitions (the structural and well-founded tables that `unfold` and `simp [f]` read), matcher information, the smart-unfolding auxiliary definitions and docstrings are not carried either, and neither is any tactic code: Mathlib's `ring`, `linarith`, `norm_num`, `positivity`, `gcongr` and `aesop` are code and attribute tables, which a replay does not carry, so a session on a replayed library has Lean core's tactics only. A prover works with the API lemmas of a replayed constant, not with its unfolding (I5). A replayed module is searchable, and those are active only through the scoped layer of
a topic (I4). Structure instance notation (`{ x := 1 }`, `{ p with x := 2 }`) needs more than the structure information: the structure's flat constructor `S.mk._flat_ctor`, an abbreviation Lean adds with every structure, and its projections.
These are constants of their own. An export of the closure of some theorems holds them only if a theorem mentions them (the flat constructor has an internal name, so not even the exporter's default mode writes it), so a
promotion that wants a structure constructible with `{ }` names them as roots (`tests/replay/check_struct_inst.lean` shows an export with and without); the transplant does not do this yet. The default value of a structure field
(`S.f._default`) is the same kind of constant, and `{ }` notation asks for the fields whose defaults are missing.

## Consequences
- The source of a promoted theorem is its export (hashed, in `data/`), not a Lean file; readable statements come from the statement text carried by Tengoku's record and are checked against the replayed constant by isnad id (the promotion lens, ADR-0003).
- A replayed constant has no compiled code (no IR): it can be checked, applied and rewritten with, not evaluated. That is all a prover needs; anything that must run is written in Tengai itself.
- An independent checker re-checks the `.olean` snapshot (I1), as Tengoku's nightly does.
- Whether the foundation fits C_load is measured next on a built module; if it does not, the foundation is trimmed (fewer, higher-leverage theorems), never the cap.

## Layers (2026-11-21)
One module holding everything promoted is loaded whole by every session, so the cold import grows with the library and meets C_load (measured: +0.093 s for 5,000 theorems, one module). A promotion is therefore a **stack of
layers**: a foundation layer holding the constants more than one topic needs, and one layer per topic holding the constants only it needs, each importing the layers it depends on. A session imports the layers
of the topic it works in and nothing else. The mechanism is two options of `tengai-replay`: `--import MODULE` starts the replay from an earlier layer (found on `LEAN_PATH`) instead of Lean core alone, and `--only NAMES.jsonl`
adds only the declarations whose first name is listed (an inductive block is one unit, its constructors and recursors come with it); everything else of the export is read and left out. Every layer is
kernel-checked on its own, so a layer that names a constant whose dependency is in no imported layer is refused. Which constant goes in which layer is a property of the dependency closures: a constant's layer is
decided by the set of topics whose closure holds it, and a constant's dependencies are used by at least the topics that use it, so the foundation never depends on a topic layer.

### Each layer is its own process
A promotion writes one module per layer, and each layer is written by its own `tengai-replay` process, which reads the whole export again. This is on purpose. Lean writes one module per process: the exports of two
premise-selection extensions (`symbolFrequency` and `sineQueNon`) read process-wide caches (`localSymbolFrequencyMapRef`, `symbolFrequencyMapRef`, private to Lean), so a process that writes several modules gives every later one the
first one's data. It was tried on 2026-11-21 (a `--layers PLAN` mode that reads and parses the export once and replays every layer from it): the counts and the sizes of the layers equalled those of one process per layer, but the
`sineQueNon` trigger of the second layer of a three-layer fixture was `HAdd.hAdd` where a fresh process writes `Fx.shared`. Recomputing the first extension's entry per layer is not enough (the second reads the first's
imported cache), and the caches cannot be reset from outside Lean. The cost of a layer is therefore, without more, one reading of the export: on the test fixture (6.5 million lines) a layer that adds one constant takes 15 s, nearly all of it reading; in tenro's wide run (4,800 theorems, 17 layers, `docs/transplant.md`) the 15 small layers took 1 min 13 s to 1 min 48 s each, most of it the same reading.
So the export is parsed once and kept. `tengai-replay EXPORT --save-tables TABLES` writes the parsed export (names, levels, expressions and declaration lines; terms and declarations are kept more compactly since 2026-11-22, below) in the format of an `.olean` (`saveModuleData`, which keeps the sharing of the expression DAG that a copy line by line would lose), and
`tengai-replay --tables TABLES --module ...` replays from it, mapped, without reading a line of JSON. Each layer is still its own process, so Lean's caches are fresh, and the module it writes is byte for byte the one a replay from the export writes (a test, with `--ext`, binder fixes and `--import`/`--only`).
On the fixture a layer that adds one constant takes about half a second where it took 15 s; the file is written once (26 s on the fixture, 303 MB) and read by every layer. `tengai-replay (EXPORT | --tables TABLES) --added-only FILE` writes the names a replay would add (the input of `tengai-extinfo`) without replaying: a declaration Lean core already holds is left out, an inductive block adds its types, constructors and recursors; on the fixture it finds the same 111 names as the replay's own `--added`, in half a second from the table file, which spares a kernel replay of the whole export just to learn them.

## Statements exports and `--stub-refused` (2026-11-21)

A statements export (`lean4export --statements`, tenro `docs/statements.md`) writes a theorem as an axiom of its type, so a replay holds the statements of a whole tree in a fraction of the space (the wide sample: 2.4 million lines against 44.8 million, +0.011 s of cold import against +0.138 s). It is a base for search, not for checking (I1): a proof found in it is checked where the real proofs are.

What a theorem standing as an axiom cannot do is be **computed through**: a definition whose value makes the kernel reduce a recursor on an auxiliary proof (`Rat.instEncodable`: `And.rec` on `_proof_1 ..`) is refused when the proof is an axiom. The exporter keeps the theorems that a definition's value mentions with their proofs, and `tengai-replay --stub-refused` is the net under that rule: a definition, opaque constant or theorem that the kernel still refuses is added as an **axiom of its type** and its name is recorded (`replay.refused`), instead of stopping the replay. The type is what a search needs of a definition; what is lost is its computation, and the manifest of a snapshot says how many were stubbed. Without the option a refusal stops the replay, as before.

## The parsed tables keep terms as records and declarations as text (2026-11-22)

The table file above held every term as an `Expr` object and every declaration as a parsed `Json` tree. On the whole Tengoku tree as one export (69.3 million lines, 62.3 million terms) the parse peaked at 15.4 GB on a 16 GB runner (tenro run 45021157759): it fitted, barely. Measured on Init (6.1 million terms, 58 thousand declarations) the memory is not in the parse but in `saveModuleData`: its compactor keeps an entry per object, so a term costs about 250 bytes in all (the object, its slot, its entry, its place in the output buffer) and a parsed declaration about forty objects.

`--save-tables` now reads a term line into a **record** of 5 to about 20 bytes (a tag byte and 4-byte ids: `CompactExprs`, two byte arrays and the literals aside) and builds no `Expr`; a declaration is kept as its **text line** with the first name it declares. A layer's process builds into `Expr`s only the terms its own declarations reach (an explicit stack, post-order, a memo by term id so that an id is one object, as it was in the eager reader), and parses only the declaration lines it replays (`--only` filters on the kept name). The module a layer writes is still byte for byte the one a replay from the export writes: the fixture test compares them, and so does Std exported by the pinned `lean4export` (10.4 million lines, 9.75 million terms; 164,767,408 bytes, sha256 `51de1349…e13d`). A table file of the old shape is refused (it has no `recs`); the workflows write and read it within one run. The direct replay of an export (no tables) is unchanged.

On Init `--save-tables` peaks at 403 MB where it peaked at 1,713 MB, and the file is 108 MB where it was 303 MB. What this has not been measured on is the whole tree: names and declaration lines scale 19 to 24 times from Init and terms 10 times, so about 6 to 8 GB is expected, not known. A layer that reaches every term of Std peaks 9 % higher than the eager replay (1,613 against 1,478 MB) (the memo map costs more per term than an array slot) and a layer that reaches a fraction pays only for that fraction.

## Scoped instances are carried with their namespace (2026-11-22)

`tengai-extinfo` read instances from `instanceExtension.getState`, which holds the global entries and those of the namespaces that are open, and none is open when a module is imported: a scoped instance of the source was never seen. Of the 1,076,224 extension rows of the whole tree (tenro run 45023256808) 42,314 said `inst` and none said `scoped`; Mathlib's `Classical.propDecidable`, its pointwise instances and every `scoped instance` of the intake libraries were not carried at all, whatever `--scoped-instances` said (that option only chose how the global ones are registered).

`tengai-extinfo` now reads the entries the extension keeps for each namespace and writes `{"n": ..., "sinst": [{"ns": [...], "prio": N}, ...]}`, sorted; `tengai-replay --ext` registers each one scoped in its namespace (`addInstance` with the namespace as the current one; `ExtCounts.scopedInstances`), so it stays inactive until that namespace is opened, as in the source. The fixture has `Fx.Scp.instTgBool`: found after `open Fx.Scp`, not found without it, not there at all in a replay without the rows, and the rows read back from the replayed module are the source's. A constant that is a global instance and a scoped one in several namespaces has an `inst` row and a `sinst` row. `--scoped-instances` keeps its meaning for the global ones; a scoped registration that Lean refuses is counted in `failed` like any other entry.

## Instances are added as the source holds them (2026-11-22)

The first whole-tree comparison of a snapshot (tenro, run 45024074369) lost five instances to `Unknown constant`, and the whole-tree replay after it four. Reproduced on a small example and confirmed at scale (tenro DIAG run 45042881274: `kernel.find?=true find?=false map₂=true` for each): since Lean 4.34 `Environment.addDeclCore` keeps the constants it adds in a registry keyed by their name **without the private prefix** (`AsyncConsts.add`), and the second constant that has a name taken panics there (printed on stderr, then ignored) and is not found by `Environment.contains` or `find?`, although the kernel holds it and it is written to the module. Two private constants of different modules with the same user-facing name (every module has its own private names in Tengoku: `TDA.Persistence.GradedFree.instHasBinaryBiproductsPModule` is one in two modules of TdaLib) are ordinary there and a collision in a replayed layer, which puts many modules into one environment. Everything that asks Lean's lookups about such a constant fails, and `addInstance` asks several times (the constant, its type, the constants its type mentions).

`tengai-extinfo` therefore writes, with an instance, **the entry as the source holds it**: the keys of its discrimination-tree path and the order its arguments are synthesised in (`keys`, `synth`; also for each namespace of a scoped instance), and `tengai-replay --ext` adds that entry as it is (`instanceExtension.addCore`), the value being the constant with the level parameters the KERNEL gives it. Nothing is recomputed: no lookup of the replayed environment, no unfolding that may differ from the source's, and the entry is exactly Tengoku's (the rows read back from the replayed module are equal, keys included: a test). A row without `keys` (a file of an older tool) is computed by `addInstance` as before. The fixture has two modules with a `private instance Fx.instCollide` each: both are carried and found; the same rows without keys lose one (a control, to be dropped with a Lean that does not have the collision). The other entries do not look constants up (reducibility, projection and structure information) or do so once (`addClass` reads the class's declaration, so a PRIVATE class whose user-facing name is taken would be lost the same way: the whole tree has none, its four losses were all instances).
